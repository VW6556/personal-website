Linux 音效無聲：SoundWire ACPI Machine Driver 排查與修復

Ubuntu 24.04 播放 YouTube 完全無聲，PipeWire 只顯示 Dummy Output。SoundWire 裝置與驅動程式皆正常，但 sof_sdw 機器驅動從未載入。問題根源在核心的 ACPI 機器匹配表缺少此款硬體組合，需手動修補並重新編譯核心模組才能解決。

Ubuntu 24.04 LTS MSI Raider 16 Max HX B2 Intel ARL-S SoundWire / SOF Kernel 6.17.0-1017-oem 核心模組修補 已解決 2026-04-09

問題現象

有聲音

  • Windows（雙開機）
  • 其他 Linux 發行版（不受影響）

無聲音

  • Ubuntu 24.04（所有聲音輸出）
  • YouTube、系統音效、音樂播放器

GNOME 音量設定只顯示 Dummy Output，找不到任何喇叭或耳機裝置。

系統偵測到的硬體

  • SoundWire 裝置存在於 sysfs
  • RT712 SDCA 驅動已綁定
  • RT1320 × 2 驅動已綁定
  • sof_sdw 機器驅動未載入

Linux 音效堆疊架構

理解音效堆疊有助於快速定位問題層級。從硬體到應用程式，每一層都有獨立職責。任何一層出問題都會造成無聲，但症狀各有不同。
層級元件職責本次狀態
硬體RT712 SDCA、RT1320 × 2實體音訊編解碼器與功率放大器✅ 正常（SoundWire 已偵測）
匯流排驅動SoundWire Intel 驅動管理 SoundWire 鏈路通訊✅ 正常
Codec 驅動rt712-sdca、rt1320-sdw驅動各別音訊晶片✅ 已綁定
機器驅動sof_sdw（ACPI 機器表匹配）將 codec 組合為完整音效卡❌ 匹配失敗，未載入
韌體 DSPSOF（Sound Open Firmware）執行 DSP 上的音訊處理拓撲⏸ 等待機器驅動
核心音效ALSA提供核心層音效裝置介面⏸ 僅 Dummy Output
應用層PipeWire / WirePlumber管理音效路由與應用程式連接⏸ 僅看到 Dummy Output

排查過程

確認 PipeWire / WirePlumber 狀態
執行 wpctl status，輸出只有 Dummy Output，完全沒有真實音效裝置。確認問題不在應用層或設定層。
確認 SoundWire 裝置已被偵測
ls /sys/bus/soundwire/devices/ 顯示三個 SoundWire 裝置： sdw:0:0:025d:0713:01（RT712 SDCA）、 sdw:0:2:025d:1320:01:0、 sdw:0:2:025d:1320:01:1（2 個 RT1320）。 硬體層正常，問題在更上層。
確認 Codec 驅動已成功綁定
readlink /sys/bus/soundwire/devices/sdw:0:0:025d:0713:01/driver 顯示 rt712-sdca。 RT1320 也已綁定 rt1320-sdw。驅動層正常，問題在機器驅動層。
發現：sof_sdw 機器驅動從未載入
lsmod | grep sof_sdw 無輸出。查閱核心原始碼確認：snd_soc_acpi_intel_arl_sdw_machines[] 表中完全沒有 RT712 SDCA（0x0713）搭配 RT1320 的組合項目，導致 ACPI 機器匹配失敗。
第一次修補：只加入 1 個 RT1320，仍然失敗
首次修補加入 RT712（0x0713）+ 單一 RT1320 的 entry，重開機後 sof_sdw 仍未載入。 深入排查發現：link 2 上有兩個 RT1320（uid=0 和 uid=1）， ACPI 機器匹配演算法要求精確比對所有已偵測裝置，缺一不可。
第二次修補：加入雙 RT1320 + RT712，成功解決
更新修補內容，在 link 2 同時定義 uid=0（左聲道）和 uid=1（右聲道）兩個 RT1320。 重新編譯模組、部署、重開機後 sof_sdw 成功載入，YouTube 恢復聲音。

根本原因詳解

ACPI 機器匹配表缺少此款硬體組合
Linux 核心模組 snd-soc-acpi-intel-match.ko 內的 snd_soc_acpi_intel_arl_sdw_machines[] 陣列定義了所有已知的 ARL 平台音效硬體組合。 若偵測到的 SoundWire 裝置組合不在表中，sof_sdw 就永遠不會載入， 導致 ALSA 只能產生 Dummy Output。

ACPI 機器匹配演算法

匹配時核心會比對兩個條件，兩者皆須完全符合：

  1. link_mask：哪些 SoundWire 鏈路（link 0～3）有裝置存在（以位元表示）
  2. links[]：每條鏈路上的裝置清單，包含每個裝置的 ADR（唯一位址）
精確匹配，不允許多也不允許少。 若表中定義 1 個 RT1320，但硬體有 2 個，匹配立即失敗。 同型號、不同 unique_id 的晶片在核心眼中是完全獨立的裝置。

SoundWire ADR 格式

每個 SoundWire 裝置以 64 位元 ADR 唯一識別，格式如下：

位元範圍欄位本機範例值說明
[51:48]link_id0 / 2SoundWire 鏈路編號（0～3）
[47:44]version3（固定）SDCA 版本，通常為 3
[43:40]unique_id0 / 1同鏈路同型號的序號，用以區分多顆
[39:24]mfg_id0x025D（Realtek）MIPI 製造商 ID
[23:8]part_id0x0713 / 0x1320晶片型號
[7:0]class_id0x01SDCA 裝置類別

本機三個裝置的 ADR 值：

RT712 SDCA（link 0, uid 0）：0x000030025D071301
RT1320 #1  （link 2, uid 0）：0x000230025D132001
RT1320 #2  （link 2, uid 1）：0x000231025D132001

本機硬體 vs 核心既有定義

比較項目核心既有最接近 entry本機硬體（MSI Raider）
Link 0 CodecRT722 SDCA（0x0722）RT712 SDCA（0x0713）
Link 2 Amp 數量RT1320 × 1（uid=0）RT1320 × 2（uid=0 + uid=1）
匹配結果—❌ 兩個條件均不符

在既有程式碼中加入以下三段定義：

/* ① RT712 SDCA 的兩個端點（headset jack + DMIC） */
static const struct snd_soc_acpi_endpoint rt712_sdca_endpoints[] = {
    { .num = 0, .aggregated = 0, .group_position = 0, .group_id = 0 },
    { .num = 1, .aggregated = 0, .group_position = 0, .group_id = 0 },
};

/* ② RT712 SDCA 裝置（link 0, uid 0） */
static const struct snd_soc_acpi_adr_device rt712_sdca_0_adr[] = {
    {
        .adr = 0x000030025D071301ull,
        .num_endpoints = ARRAY_SIZE(rt712_sdca_endpoints),
        .endpoints = rt712_sdca_endpoints,
        .name_prefix = "rt712"
    }
};

/* ③ 雙 RT1320（link 2：uid=0 左聲道，uid=1 右聲道，聚合為 group 1） */
static const struct snd_soc_acpi_adr_device rt1320_2_dual_adr[] = {
    {
        .adr = 0x000230025D132001ull,
        .num_endpoints = 1,
        .endpoints = &spk_l_endpoint,
        .name_prefix = "rt1320-1"
    },
    {
        .adr = 0x000231025D132001ull,
        .num_endpoints = 1,
        .endpoints = &spk_r_endpoint,
        .name_prefix = "rt1320-2"
    }
};

/* ④ 組合鏈路陣列 */
static const struct snd_soc_acpi_link_adr arl_rt712_l0_rt1320x2_l2[] = {
    { .mask = BIT(0), .num_adr = ARRAY_SIZE(rt712_sdca_0_adr),  .adr_d = rt712_sdca_0_adr  },
    { .mask = BIT(2), .num_adr = ARRAY_SIZE(rt1320_2_dual_adr), .adr_d = rt1320_2_dual_adr },
    {}
};

/* ⑤ 在 snd_soc_acpi_intel_arl_sdw_machines[] 末尾加入新 entry */
{
    .link_mask = BIT(0) | BIT(2),
    .links = arl_rt712_l0_rt1320x2_l2,
    .drv_name = "sof_sdw",
    .sof_tplg_filename = "sof-arl-rt722-l0_rt1320-l2.tplg",

Lesson Learned

Dummy Output ≠ 硬體損壞

PipeWire 顯示 Dummy Output，不代表音效晶片壞了。通常是 ALSA 層以下的機器驅動未載入。先確認 SoundWire/ACPI 層，再往上排查，而非重裝驅動或系統。

ACPI 機器匹配是嚴格全比對

Linux 核心的機器匹配演算法要求完全吻合所有 SoundWire 裝置。哪怕只多一顆同型晶片（不同 unique_id），整個匹配就失敗。新款筆電常因核心未及時更新匹配表而無聲。

unique_id 決定裝置唯一性

同型號的兩顆 RT1320 晶片（uid=0 和 uid=1）在核心看來是完全不同的裝置。ADR 中 bits [43:40] 才是 unique_id，bits [51:48] 才是 link_id——讀法容易搞混，需要細心解碼。

出樹外模組是短期解法

編譯 out-of-tree 核心模組可不動整個核心直接替換單一 .ko 檔。但每次核心更新後須重新編譯。正確做法是向上游提交 patch，讓核心官方支援此硬體。

拓撲檔案（.tplg）是 DSP 藍圖

SOF 拓撲檔定義 DSP 上的音訊處理管線。新版核心支援以 SDCA function-based 拓撲（sof-sdca-jack-id0.tplg、sof-sdca-2amp-id2.tplg）取代單一大型 .tplg，實現跨 codec 通用化。

排查方向：由下而上

音效問題排查順序：硬體偵測 → 匯流排驅動 → Codec 驅動 → 機器驅動 → DSP/SOF → ALSA → PipeWire → 應用層。在哪一層中斷就在哪一層解決，不要跳層。

新款 Intel 筆電在 Ubuntu 24.04 的建議做法： 若音效出現 Dummy Output，優先安裝最新 OEM 核心（linux-oem-6.17）並更新 firmware-sof-signed。 若仍有問題，查閱 SOF Project Issues 是否有對應的硬體支援 patch。
